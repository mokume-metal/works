# Prism — 光をプリズムに通す

![入射角 50 度、白色光が虹に分かれる](https://i.gyazo.com/8cdd62d2b8a51d6bab10d2433f24523c.png)

制作トラック ([mokume ADR-0022](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0022-production-track.md)) の 8 本目。

**絵を作り込むのではなく、幾何光学を回してその帰結として虹が出る形にしてある。** 波長ごとに Cauchy の式で屈折率を決め、面ごとに Snell で曲げ、臨界角を越えたら全反射させ、フレネルで反射と屈折へ力を分ける。虹はその結果として出てくるので、**分散を 0 にすれば消える**し、入射角を浅くすれば**紫から順に閉じ込められる**。

既存 7 本が通っていない経路が 3 つあった。**CPU で毎フレーム幾何を組み立てる**こと (Nebula の 100 万粒は仕事が全部 GPU 側だった)、**分光を色にする**こと、そして**触って動かせる**ことである。

![入射角 60→40 度を掃き、全反射の窓で紫から剥がれる](https://i.gyazo.com/5bff91022f5884d71ef939ce08e2eaa9.webp)

> 撮影範囲: 走っているスケッチの面だけ (`mokume mcp` の観測が書き出した絵で、画面は撮っていない)。放っておくと走る自動の往復から 9 秒ぶんを 1 枚おきに 45 枚取り、折り返して 88 枚・15fps・約 6 秒にしたもの。**1 枚では読めないものを見てほしい** — 入射角が浅くなるにつれて**紫から順に色が剥がれ落ち**、剥がれたぶんが硝子の中で全反射して別の向きへ出ていく。これは手で描いた虹には出せない。

## 走らせる

```bash
mokume run Prism -c release    # 作って走らせる
mokume watch Prism -c release  # 保存したら作り直して差し替える
mokume mcp Prism               # 走っているスケッチを外から観測する
```

**`-c release` を付ける。** `run` / `watch` の既定は debug で、**この作品はそこで 18.6fps まで落ちる** (下記「速さ」)。works で初めて、毎フレームの仕事の大半が CPU にある作品だからである。

## 触る

| 操作 | 効くもの |
| --- | --- |
| マウスを動かす | **光源が動く。** 狙いは常に硝子の重心なので、動かすと入射角が変わる |
| ドラッグ | **硝子を掴んで回す。** 重心とマウスの角度差をそのまま向きに写す |
| スクロール | **分散の強さ (Cauchy の B)。** 0 で虹が消え、上げると扇が開く |
| スペース | 自動の往復へ返す |
| R | はじめの置き方へ戻す |

**触られていない間は自動で往復する** — 入射角 40〜60 度を 16 秒周期で掃き、端の 6 度が下記の全反射の窓に入る。手で触ると手動へ移り、6 秒放っておくと自動へ戻る (跳ばないよう補間してある)。

### 分散を 0 にすると、虹が消える

| 分散 0 | 分散 0.0200 (既定) | 分散 0.0320 |
| --- | --- | --- |
| [![](https://i.gyazo.com/698152130e60c67d06fe2d9fdce31246.png)](https://i.gyazo.com/698152130e60c67d06fe2d9fdce31246.png) | [![](https://i.gyazo.com/8cdd62d2b8a51d6bab10d2433f24523c.png)](https://i.gyazo.com/8cdd62d2b8a51d6bab10d2433f24523c.png) | [![](https://i.gyazo.com/45544cbda6d45887364fce9353d431fc.png)](https://i.gyazo.com/45544cbda6d45887364fce9353d431fc.png) |
| 白いまま曲がるだけ | 扇が 153 画素 | 扇がおよそ 1.6 倍に開く |

**屈折率が波長によらなければ、白い光は白いまま曲がる。** 虹は「曲がったから」ではなく「波長ごとに曲がり方が違うから」出る — スクロールでその 1 点だけを動かせるようにしてある。数字は入射角 50 度でのもの (受け面の上で赤と紫が離れる距離)。

分散を上げ切ると、計算上は 434nm より短いところが受け面の下端から外れる。**それでも絵は欠けない** — その帯域は等色関数がほぼ 0 で、元から目に見えるだけの重みを持っていないためである。

## どの mokume で描いたか

**`Package.resolved` が固定している版がそのまま答えで、コミットしてある。** この作品のコミットを checkout すれば mokume も当時の版に戻るので、別の作品が新しい mokume を要求してピンが動いても、ここの再現は壊れない。

**同じフレーム番号からは同じ絵が出る** (mokume の [ADR-0001](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0001-founding-principles.md) 原則 2)。この作品は乱数を使わず、時計はフレーム番号から導かれる。**触っていない限り、同じ番号のフレームは同じ絵になる。**

**絵のハッシュは持っていない**ので、版を上げて何かが動いたことに気付くのは窓を開けて目で見たときである。

## 何がどう動いているか

### 描いているのは光ではなく、散った光である

真空を進む光は横から見えない。**ここに見えている帯は「微小な塵が横へ散らしたぶん」という約束**で、だから強度は光の力に比例し、進むほど暗くなる (空気は 2600 画素、硝子は 1800 画素で `1/e`)。

**硝子の中だけ散乱を 1.6 倍にしてある。これは見せるための嘘である。** 硝子の中の扇は 300 画素で数画素しか開かないので、外と同じ濃さで描くと白い塊にしか見えない。物理ではなく、中で何が起きているかを読ませるための倍率である。

### 線ではなく、幅を持つ帯を追う

**光線を線で引くと、どれだけ本数を積んでもレーザーの束にしか見えない。** 太さと隙間の競争から逃げられないからである。

ここでは波長ごとに**中心線と幅**を持つビームを追い、断面の明るさを `(1 − u²)^1.5` で端が 0 に落ちるようにしてある。隣り合う波長の帯が裾で混ざるので、扇は連続したグラデーションになる。1 区間は幅方向に 4 つに割った三角形 8 枚で、**全部を `beginShape(.triangles)` 1 本に積む** — 頂点ごとに `fill()` を変えられるので (Ring と同じ手)、幅方向のフェードも進むほど暗くなる勾配も頂点の色だけで出る。

**屈折すると束は伸び縮みする** (`cos θ_out / cos θ_in`)。その比を持ち回って**帯の幅に掛け、色を割っている** — 広がったぶんだけ薄くなるので、力は保たれる。

### 波長は 1/λ² を等間隔に刻む

偏角は屈折率にほぼ比例し、屈折率は Cauchy の式そのままで **1/λ² に厳密に比例する**。だから λ を等間隔に刻むと**扇の中では等間隔にならない** — `dn/dλ = −2B/λ³` は 400nm で 700nm の 5.3 倍あるので、**赤い側だけ隙間が開いて縞になる**。

1/λ² を等間隔に 160 本刻めば、扇の中の角度がほぼ等間隔に並ぶ。**帯域の重み `λ³` (ヤコビアン) を掛ける**のを落とすと、青が過剰に重くなる。

### 色は Planck 則から作り、線形 Display P3 へ写す

光源の分光は**表を持たず Planck 則 (6000K) で作る**。3 行で書けて、紫の端が自然に暗くなるので「白色光」を作品が自分で説明できる。波長 → XYZ は Wyman・Sloan・Shirley (JCGT 2013) の多ローブ当てはめ。

**XYZ → 線形 sRGB ではなく、線形 Display P3 で写す。** mokume の作業空間は extended Display P3 なので (`LinearRGBA` のドキュメントと [ADR-0011](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0011-color-model.md) 決定 1)、sRGB の行列で作った値を渡すと広い原色で再生されて過飽和し、色相もずれる。

単色光は必ずどれかの成分が負になるが (特に 480〜510nm と 400〜430nm)、**0 で切らず中性軸へ寄せて**輝度を戻している — 成分ごとに切ると色相と明るさの両方が動く。正規化は**成分ごと**に行う (行列の行和が 1.159 / 0.957 / 0.917 と揃っていないので、スカラー 1 つで割ると白がピンクに寄る)。

### 見せ場は全反射の窓

正三角形・n = 1.641〜1.725 では、**2 枚目の面から出られる入射角の下限が波長ごとに違う**。

| | 出られる入射角 |
| --- | --- |
| 赤 (700nm, n = 1.6408) | **38.8 度**より大きいこと |
| 紫 (400nm, n = 1.725) | **45.9 度**より大きいこと |

つまり入射角 45.9 度を割ると**紫から順に閉じ込められ**、38.8 度を割ると全部が消える。自動の往復はこの 7 度を必ず横切るように振ってある (上のアニメーション)。剥がれた光は硝子の中で全反射し、別の面から出ていく。

### 構図は偏角から逆に決めた

**曲がる角は 50〜60 度あり、しかも底辺の側へ曲がる。** 素直に中央へ置くと出て行った光が即座に下端から抜けて、虹の乗る面が無くなる。硝子の重心 (1000, 300)・受け面 x = 1620 という置き方は、**全反射で紫が消える直前 (入射角 46 度) にちょうど扇が面へ収まる**距離から逆算してある。

**受け面 (スクリーン) を 1 枚立てているのは、真空の光が横から見えないため**である。分かれたことが読めるのは面に落ちたときで、この 1 枚が「プリズムを通した」ことを成立させている。面に落ちた光は**面の上の線密度**として溜めるので、空中の帯とは明るさの桁が違う (幅 60 画素で入った束が 200 画素あまりに広がったところを 2.25 画素の刻みで拾うため)。

## 物理の裏取り

**最小偏角の式と突き合わせた。** 頂点角 60 度・屈折率 n のプリズムの最小偏角は `2·asin(n·sin30°) − 60°` である。これはスケッチの追跡とは独立に立つ式なので、追った結果がここへ一致するなら、交差・法線の向き・Snell のどれもずれていない。

| | 追跡が出した最小 | 式 | 差 |
| --- | --- | --- | --- |
| 赤 700nm (n = 1.6408) | 50.25 度 (入射角 55.1 度) | 50.25 度 | 0.000 |
| 緑 550nm (n = 1.6825) | 54.54 度 (入射角 57.3 度) | 54.54 度 | 0.000 |
| 紫 400nm (n = 1.725) | 59.20 度 (入射角 59.6 度) | 59.20 度 | 0.000 |

突き合わせは同じ式を別に書き下した実装で行い、スケッチの側は**観測が返す入射角**で確かめた — 光源を仕込んだ位置 (558, 461) へ置くと `incidence_deg` が 50.014 度を返し、仕込みの 50.0 度と 0.02 度で合う。

**硝子は架空である。** Cauchy の A = 1.60 / B = 0.020 は、**分散だけ実在の重フリント (SF11) 相当で、基底の屈折率を低くしたもの**。SF11 そのもの (A = 1.727) だと最小偏角が 68 度になり、曲がった先が画面から外れる。

## 速さ (2026-09-07 の実測)

観測 (`mokume mcp`) が返した数字。Apple M3 Max・40 コア GPU・macOS 26.6.2。面は 1920x1080。

| | release | debug |
| --- | --- | --- |
| 速さ | **60fps 張り付き** | **18.6fps** |
| フレーム時間 | 平均 16.67ms / 最大 16.72ms | 平均 53.8ms / 最大 109.8ms |
| 占有メモリ | 400〜408 MB | 393 MB |
| 熱 | `nominal` 〜 `fair` | `nominal` |
| 警告 | 無し | 無し |

**差は 3.2 倍で、これがそのまま「CPU 律速である」ことの証拠**である。毎フレーム 160 本の光を追って 960 区間ぶんの帯を組み立て、23,000 前後の頂点を積む — GPU 側の仕事は 1 回の描画に畳まれているので、遅くなっているのは追跡と組み立てのほうである。

`line()` を 1 本ずつ引く形も試せるが、**mokume では頂点列にまとめるほうが速いとは限らない** — `line()` は 1 本 = 1 インスタンスの距離関数経路を通り、色や太さを毎本変えても描画の列が切れない。この作品が三角形を選んだのは速さではなく、**幅方向のグラデーションが線では作れない**ためである。

## 踏んだもの

### 加算合成が 1 描画ごとに飽和するので、光を積み上げられない

mokume の [ADR-0011](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0011-color-model.md) 決定 1 は、作業空間が範囲外の値 (負値および 1.0 超) を**切り捨てない**と決めている。8 bit を採らない理由として「1.0 を超える値が保持できなければ、露出・グロー・HDR 出力といった表現は入口で失われる」とまで書いてある。

**ところが `.add` は 1 描画ごとに `clamp(s + d, 0, 1)` する** (`Drawing/Shaders/Common.metal` の `mokume_composite`)。実装のコメントは「作業空間は範囲外を許すが、ここで抑えないと混ぜた結果が下地を壊す」と理由を書いており、意図した選択である。ただし**逆転がある** — 素直に足すだけの `.blend` は乗算済みのまま加算するので 1.0 超を保持でき、**光を重ねるための `.add` だけが HDR を失う**。

**実害**: 160 本の単色光を重ねて白を作るこの作品では、芯が 1.0 に達した時点で「分かれる前」と「分かれた後」の差が消える。**白い芯を 0.52 に置き、足りない明るさを `exposure(1.35)` で足す**という形に落としたが、露出は画面全体に掛かるので暗部も一緒に持ち上がる。`BlendMode.add` の説明 ("足す。光を重ねたように明るくなる") からこの挙動は読めない。

mokume へは、この PR がマージされた後に Issue として戻す。

### 踏まなかったもの

- **文字は日本語が出る** (`text()`)。works で `text()` を使うのはこの作品が初めてなので測っておいた。手引きは日本語のまま出ている
- **`exposure` / `toneMapping` は `setup()` から効く**。画面の性質でフレームに属さないため、Nebula が粒の混ぜ方で踏んだ「`setup()` のスタイルは無視される」に当たらない
- **`constrain` / `lerp` は無い**が、`min(max(...))` と自前の補間で足りた。実害が無いので起票しない (mokume の [ADR-0008](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0008-mechanism-needs-demonstrated-harm.md) が求めるのは実害であって不足そのものではない)
