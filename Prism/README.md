# Prism — 光をプリズムに通す

![入射角 50 度、灯りから出た白色光が虹に分かれる](https://i.gyazo.com/5d4d1ed1a1b4b4bef292380902e330dd.png)

制作トラック ([mokume ADR-0022](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0022-production-track.md)) の 8 本目。

**絵を作り込むのではなく、幾何光学を回してその帰結として虹が出る形にしてある。** 波長ごとに Cauchy の式で屈折率を決め、面ごとに Snell で曲げ、臨界角を越えたら全反射させ、フレネルで反射と屈折へ力を分ける。虹はその結果として出てくるので、**分散を 0 にすれば消える**し、入射角を浅くすれば**紫から順に閉じ込められる**。

既存 7 本が通っていない経路が 3 つあった。**CPU で毎フレーム幾何を組み立てる**こと (Nebula の 100 万粒は仕事が全部 GPU 側だった)、**分光を色にする**こと、そして**触って動かせる**ことである。

![入射角 40→60 度を掃き、全反射の窓で紫から剥がれる](https://i.gyazo.com/2d64ff119b53874736dda7436514a3e2.webp)

> 撮影範囲: 走っているスケッチの面だけ (`mokume mcp` の観測が書き出した絵で、画面は撮っていない)。放っておくと走る自動の往復から 8 秒ぶんを 10 フレームおきに 48 枚取り、折り返して 94 枚・15fps・6.3 秒にしたもの (入射角 40.1 → 60.0 度)。**1 枚では読めないものを見てほしい** — 入射角が浅いあいだは**紫から順に色が剥がれ落ちて**いて、剥がれたぶんは硝子の中で全反射して別の向きへ出ていく。灯りが弧を描いて動くので、**光源とプリズムの関係が変わっていること**もそのまま見える。

## 走らせる

```bash
mokume run Prism -c release    # 作って走らせる
mokume watch Prism -c release  # 保存したら作り直して差し替える
mokume mcp Prism               # 走っているスケッチを外から観測する
```

**`-c release` を付ける。** `run` / `watch` の既定は debug で、**この作品はそこで 18.6fps まで落ちる** (下記「速さ」)。works で初めて、毎フレームの仕事の大半が CPU にある作品だからである。

## 触る

| 操作 | 効くもの |
| --- | --- |
| マウスを動かす | **灯りごと光源が動く。** 狙いは常に硝子の重心なので、動かすと入射角が変わる |
| ドラッグ | **硝子を掴んで回す。** 重心とマウスの角度差をそのまま向きに写す |
| スクロール | **分散の強さ (Cauchy の B)。** 0 で虹が消え、上げると扇が開く |
| スペース | 自動の往復へ返す |
| R | はじめの置き方へ戻す |

**触られていない間は自動で往復する** — 入射角 40〜60 度を 16 秒周期で掃き、端の 6 度が下記の全反射の窓に入る。手で触ると手動へ移り、6 秒放っておくと自動へ戻る (跳ばないよう補間してある)。

### 分散を 0 にすると、虹が消える

| 分散 0 | 分散 0.0200 (既定) | 分散 0.0320 |
| --- | --- | --- |
| [![](https://i.gyazo.com/0ff85a93ce9b1d4f38571eaf19325d08.png)](https://i.gyazo.com/0ff85a93ce9b1d4f38571eaf19325d08.png) | [![](https://i.gyazo.com/5d4d1ed1a1b4b4bef292380902e330dd.png)](https://i.gyazo.com/5d4d1ed1a1b4b4bef292380902e330dd.png) | [![](https://i.gyazo.com/353621ff54a9bf66ae2943835dc802a7.png)](https://i.gyazo.com/353621ff54a9bf66ae2943835dc802a7.png) |
| 白いまま曲がる (筋は 54 画素 = 束の幅) | 受け面の筋が 163 画素 | 390 画素 |

**屈折率が波長によらなければ、白い光は白いまま曲がる。** 虹は「曲がったから」ではなく「波長ごとに曲がり方が違うから」出る — スクロールでその 1 点だけを動かせるようにしてある。3 枚とも入射角 50.014 度・光源 (558, 461) で撮ってあり、筋の高さは受け面の手前 (x = 1613) を縦に読んだ値である。

**分散 0 の筋は束の幅そのもの**で、そこから広がったぶんが分散である。既定の 0.0200 では筋が y = 632…794 に出るが、独立に組んだ計算は**赤 641 / 紫 794** と言う — 下端がぴたりと合う (上端が少し高いのは束が幅を持っているため)。

**上げていくと、まず紫が全反射に捕まる。** 入射角 50 度では屈折率 1.769 が境で、0.0320 なら **435nm より短い光が硝子から出られない** (その手前の波長は y = 1049 まで伸びる)。上限の 0.0550 まで上げると 570nm より短い光まで捕まり、**扇は赤から橙だけになる。**

## どの mokume で描いたか

**`Package.resolved` が固定している版がそのまま答えで、コミットしてある。** この作品のコミットを checkout すれば mokume も当時の版に戻るので、別の作品が新しい mokume を要求してピンが動いても、ここの再現は壊れない。

**同じフレーム番号からは同じ絵が出る** (mokume の [ADR-0001](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0001-founding-principles.md) 原則 2)。この作品は乱数を使わず、時計はフレーム番号から導かれる。**触っていない限り、同じ番号のフレームは同じ絵になる。**

**絵のハッシュは持っていない**ので、版を上げて何かが動いたことに気付くのは窓を開けて目で見たときである。

## 何がどう動いているか

### 描いているのは光ではなく、散った光である

真空を進む光は横から見えない。**ここに見えている帯は「微小な塵が横へ散らしたぶん」という約束**で、だから強度は光の力に比例し、進むほど暗くなる (空気は 1400 画素、硝子は 1200 画素で `1/e`)。

**この距離を短く取っているのは、束を棒に見せないためである。** 2600 画素にしていたときは、光路が 250 画素しかない区間では端から端まで濃さが変わらず (実測で 96% が残る)、平らな板が置いてあるようにしか見えなかった。1400 画素なら同じ区間で 89% になり、進むほど細って見える。

硝子の中だけ散乱を 1.1 倍にしてある。**これは見せるための嘘だが、倍率は 1.6 から下げた** — 芯が 220/255 まで持ち上がると、出したかった縁の色が階調の肩で白く潰れるためである。

### 線ではなく、幅を持つ帯を追う

**光線を線で引くと、どれだけ本数を積んでもレーザーの束にしか見えない。** 太さと隙間の競争から逃げられないからである。

ここでは波長ごとに**中心線と幅**を持つビームを追い、断面の明るさを `(1 − u²)^1.5` で端が 0 に落ちるようにしてある。隣り合う波長の帯が裾で混ざるので、扇は連続したグラデーションになる。1 区間は幅方向に 6 つに割った三角形 12 枚で、**全部を `beginShape(.triangles)` 1 本に積む** — 頂点ごとに `fill()` を変えられるので (Ring と同じ手)、幅方向のフェードも進むほど暗くなる勾配も頂点の色だけで出る。

**刻みは 4 では足りなかった。** 重みが 0 / 0.65 / 1 の折れ線になるので芯のまわりが平らな高原になり、束が板に見える。6 つに割ると肩が丸くなる。

**光源から硝子までの 1 区間だけは、波長ごとに描かない。** そこはまだ光が分かれていない = 160 本の同じ三角形が重なるだけで、しかも `Spectrum` が成分ごとに正規化してあるので**足し合わせると厳密に白**である。1 本の白い帯として置けば絵は変わらず、頂点は 160 分の 1 になる。**分かれるのは面に当たってからだ**という筋書きとも一致する。

**屈折すると束は伸び縮みする** (`cos θ_out / cos θ_in`)。その比を持ち回って**帯の幅に掛け、色を割っている** — 広がったぶんだけ薄くなるので、力は保たれる。

### 光は面の上で折れる — だから面に足跡を置く

**区間の端どうしが宙で突き合わさっているだけだと、折れているのが面の上だと読めない。** 帯が 2 本並んでいるようにしか見えず、屈折が起きた場所が絵から消える。

そこで**光が面を横切った跡を、波長ごとに置く**。足跡の長さは束の幅を入射角の余弦で割ったもの (斜めに当たれば伸びる) で、明るさは運んでいた力に比例する。**入口では 160 本ぶんが重なって白い筋**になり、**出口では波長ごとに 8〜13 画素ずれて並ぶので、面の上に小さな虹の筋**が出る。硝子の中で分かれていたことが、出た瞬間ではなく面の上で読める。

入口・出口・全反射を**区別していない**。どれも「面を光が横切った」ことで、違いは運んでいた力だけだからである (全反射の点だけを光らせる前の作りは、この仕組みへ畳んだ)。

### 灯りは自分の滲みを隠す

光源が線 2 本だと、束が宙で唐突に始まって切り口が見える。ここでは絞った口を持つ灯りとして描いている。

| | |
| --- | --- |
| 胴 | `toward` に沿った暗い台形。**`.blend` で置いて自分の滲みを遮る** — 加算だと胴が透けて灰色の斑になり、灯りに見えない。ついでに束の切り口も覆う |
| 唇 | 口の両側の短い金属色。絞った口から出ていることが読める |
| 口 | 束の幅ぶんの白熱した芯。ここから帯が出ていく |
| 滲み | **入れ子の扇を 5 枚重ねる。** 扇 1 枚は中心から縁まで直線に落ちるので、大きく取るとただの灰色の円錐になる。細い山を積むと灯りの滲みの形になり、出口の `bloom` (閾値 0.30) が拾う |

![絞った口を持つ灯り (入射角 50 度、2 倍に拡大)](https://i.gyazo.com/46562e3aa2903c433c9b612e764c81fd.png)

### 波長は 1/λ² を等間隔に刻む

偏角は屈折率にほぼ比例し、屈折率は Cauchy の式そのままで **1/λ² に厳密に比例する**。だから λ を等間隔に刻むと**扇の中では等間隔にならない** — `dn/dλ = −2B/λ³` は 400nm で 700nm の 5.3 倍あるので、**赤い側だけ隙間が開いて縞になる**。

1/λ² を等間隔に 160 本刻めば、扇の中の角度がほぼ等間隔に並ぶ。**帯域の重み `λ³` (ヤコビアン) を掛ける**のを落とすと、青が過剰に重くなる。

### 色は Planck 則から作り、線形 Display P3 へ写す

光源の分光は**表を持たず Planck 則 (6000K) で作る**。3 行で書けて、紫の端が自然に暗くなるので「白色光」を作品が自分で説明できる。波長 → XYZ は Wyman・Sloan・Shirley (JCGT 2013) の多ローブ当てはめ。

**XYZ → 線形 sRGB ではなく、線形 Display P3 で写す。** mokume の作業空間は extended Display P3 なので (`LinearRGBA` のドキュメントと [ADR-0011](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0011-color-model.md) 決定 1)、sRGB の行列で作った値を渡すと広い原色で再生されて過飽和し、色相もずれる。

単色光は必ずどれかの成分が負になるが (特に 480〜510nm と 400〜430nm)、**0 で切らず中性軸へ寄せて**輝度を戻している — 成分ごとに切ると色相と明るさの両方が動く。正規化は**成分ごと**に行う (行列の行和が 1.159 / 0.957 / 0.917 と揃っていないので、スカラー 1 つで割ると白がピンクに寄る)。

### 見せ場は全反射の窓

正三角形・n = 1.641〜1.725 では、**2 枚目の面から出られる入射角の下限が波長ごとに違う**。

| | 出られる入射角 |
| --- | --- |
| 赤 (700nm, n = 1.6408) | **38.8 度**より大きいこと |
| 紫 (400nm, n = 1.725) | **45.9 度**より大きいこと |

つまり入射角 45.9 度を割ると**紫から順に閉じ込められ**、38.8 度を割ると全部が消える。自動の往復はこの 7 度を必ず横切るように振ってある (上のアニメーション)。剥がれた光は硝子の中で全反射し、別の面から出ていく。

### 構図は偏角から逆に決めた

**曲がる角は 50〜60 度あり、しかも底辺の側へ曲がる。** 素直に中央へ置くと出て行った光が即座に下端から抜けて、虹の乗る面が無くなる。硝子の重心 (1000, 300)・受け面 x = 1620 という置き方は、**全反射で紫が消える直前 (入射角 46 度) にちょうど扇が面へ収まる**距離から逆算してある。

**受け面 (スクリーン) を 1 枚立てているのは、真空の光が横から見えないため**である。分かれたことが読めるのは面に落ちたときで、この 1 枚が「プリズムを通した」ことを成立させている。面に落ちた光は**面の上の線密度**として溜めるので、空中の帯とは明るさの桁が違う (幅 26 画素で入った束が 160 画素あまりに広がったところを 2.25 画素の刻みで拾うため)。

## 直したこと — 四角が 2 つ並んでいるようにしか見えなかった

最初の形は、**光源が光源に見えず**、**プリズムまでの道筋と最初の内部区間が四角の組み合わせにしか見えなかった**。原因は 3 つあって、どれも絵の側の選択だった (物理は合っていた)。

| | 前 | 後 |
| --- | --- | --- |
| 硝子の中の帯の幅 | 81〜86 画素 | **37〜39 画素** |
| 帯の上端の色 (`r − b`) | −12 (硝子の地 −33 に紛れる) | **+9 (地は −10)** |
| 帯の上端 − 下端 | +31 | **+41** |
| 芯の明るさ | 211〜225 | 163〜175 |
| 空気中の芯 (光源から 50 → 250 画素) | 96% (平ら) | **89%** |

> 測り方: 観測 (`mokume mcp`) が返した PNG を `ffmpeg` で生データに落とし、入射角 50.014 度・光源 (558, 461) に固定して x = 900 / 1000 / 1100 の縦の断面を読んだ。硝子の地は同じ x の帯より上から取っている。

1. **束が太すぎた。** 硝子の中で分かれる量は出口の面で 8〜13 画素しかない。しかも束は入るときに 1.3〜1.8 倍へ広がる (`spread`) ので、60 画素で入れると中では 80〜105 画素になり、分離は 1 割そこそこに埋もれる。**26 画素**にすると中でも 37 画素で、分離が 2〜3 割を占めるので紫の縁と赤の縁として読める
2. **硝子が青かった。** 地の `r − b` が −33 だと、いちばん見せたい紫の縁 (−43) が地の色と区別できない。**冷たい灰 (−10)** にすると、赤の縁も紫の縁も両方が地から離れる
3. **芯が明るすぎた。** 220/255 まで持ち上がると階調の肩で白く潰れて、縁の色が消える

## 物理の裏取り

**最小偏角の式と突き合わせた。** 頂点角 60 度・屈折率 n のプリズムの最小偏角は `2·asin(n·sin30°) − 60°` である。これはスケッチの追跡とは独立に立つ式なので、追った結果がここへ一致するなら、交差・法線の向き・Snell のどれもずれていない。

| | 追跡が出した最小 | 式 | 差 |
| --- | --- | --- | --- |
| 赤 700nm (n = 1.6408) | 50.25 度 (入射角 55.1 度) | 50.25 度 | 0.000 |
| 緑 550nm (n = 1.6825) | 54.54 度 (入射角 57.3 度) | 54.54 度 | 0.000 |
| 紫 400nm (n = 1.725) | 59.20 度 (入射角 59.6 度) | 59.20 度 | 0.000 |

突き合わせは同じ式を別に書き下した実装で行い、スケッチの側は**観測が返す入射角**で確かめた — 光源を仕込んだ位置 (558, 461) へ置くと `incidence_deg` が 50.014 度を返し、仕込みの 50.0 度と 0.02 度で合う。

**硝子は架空である。** Cauchy の A = 1.60 / B = 0.020 は、**分散だけ実在の重フリント (SF11) 相当で、基底の屈折率を低くしたもの**。SF11 そのもの (A = 1.727) だと最小偏角が 68 度になり、曲がった先が画面から外れる。

## 速さ (2026-09-07 の実測)

観測 (`mokume mcp`) が返した数字。Apple M3 Max・40 コア GPU・macOS 26.6.2。面は 1920x1080。

| | release | debug |
| --- | --- | --- |
| 速さ | **60fps 張り付き** | **18.6fps** |
| フレーム時間 | 平均 16.67ms / 最大 16.72ms | 平均 53.8ms / 最大 67.7ms |
| 占有メモリ | 390〜428 MB | 399 MB |
| 熱 | `nominal` 〜 `fair` | `nominal` |
| 警告 | 無し | 無し |

**差は 3.2 倍で、これがそのまま「CPU 律速である」ことの証拠**である。毎フレーム 160 本の光を追い、801 本の帯と 321 個の足跡を組み立てて 35,000 前後の頂点を積む (入射角 50 度・分散 0.0200 のとき。`bands` と `spots` を観測へ差し出してある) — GPU 側の仕事は数回の描画に畳まれているので、遅くなっているのは追跡と組み立てのほうである。

**頂点を増やすと素直に落ちる。** 断面の刻みを 8 つに割った形は 53fps まで落ちた (平均 18.6ms)。6 つに割り、光源から硝子までを 1 本の白い帯にまとめて 60fps へ戻している。

`line()` を 1 本ずつ引く形も試せるが、**mokume では頂点列にまとめるほうが速いとは限らない** — `line()` は 1 本 = 1 インスタンスの距離関数経路を通り、色や太さを毎本変えても描画の列が切れない。この作品が三角形を選んだのは速さではなく、**幅方向のグラデーションが線では作れない**ためである。

## 踏んだもの

### 加算合成が 1 描画ごとに飽和するので、光を積み上げられない

mokume の [ADR-0011](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0011-color-model.md) 決定 1 は、作業空間が範囲外の値 (負値および 1.0 超) を**切り捨てない**と決めている。8 bit を採らない理由として「1.0 を超える値が保持できなければ、露出・グロー・HDR 出力といった表現は入口で失われる」とまで書いてある。

**ところが `.add` は 1 描画ごとに `clamp(s + d, 0, 1)` する** (`Drawing/Shaders/Common.metal` の `mokume_composite`)。実装のコメントは「作業空間は範囲外を許すが、ここで抑えないと混ぜた結果が下地を壊す」と理由を書いており、意図した選択である。ただし**逆転がある** — 素直に足すだけの `.blend` は乗算済みのまま加算するので 1.0 超を保持でき、**光を重ねるための `.add` だけが HDR を失う**。

**実害**: 160 本の単色光を重ねて白を作るこの作品では、芯が 1.0 に達した時点で「分かれる前」と「分かれた後」の差が消える。**白い芯を 0.52 に置き、足りない明るさを `exposure(1.35)` で足す**という形に落としたが、露出は画面全体に掛かるので暗部も一緒に持ち上がる。`BlendMode.add` の説明 ("足す。光を重ねたように明るくなる") からこの挙動は読めない。

**mokume へは [mokume#1057](https://github.com/mokume-metal/mokume/issues/1057) として戻した。**

### 踏まなかったもの

- **文字は日本語が出る** (`text()`)。works で `text()` を使うのはこの作品が初めてなので測っておいた。手引きは日本語のまま出ている
- **`exposure` / `toneMapping` は `setup()` から効く**。画面の性質でフレームに属さないため、Nebula が粒の混ぜ方で踏んだ「`setup()` のスタイルは無視される」に当たらない
- **`constrain` / `lerp` は無い**が、`min(max(...))` と自前の補間で足りた。実害が無いので起票しない (mokume の [ADR-0008](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0008-mechanism-needs-demonstrated-harm.md) が求めるのは実害であって不足そのものではない)
