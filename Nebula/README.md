# Nebula — 4K に 100 万粒を撒いて、3 次元の渦で瞬かせる

![100 万粒の星雲 (frame 1129)](https://i.gyazo.com/7bb7fa56c4040aaf6308fd2f50b8b3ca.png)

制作トラック ([mokume ADR-0022](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0022-production-track.md)) の 7 本目。**works で粒 (`makeParticles`) を使う 1 本目**である。

既存 6 作品はどれも粒にも GPU の計算 (`makeNumbers` / `makeComputation`) にも触れていない。しかも mokume 自身の参照スケッチと検査が実際に描いている粒はいちばん多いもので 24,000 (`Sketches/SparksAndForces.swift`) なので、**100 万は道具の側も一度も描いたことのない規模**だった。

**知りたかったのは 3 つ** — その数が確保できるか、4K で速さが出るか、そして**動いている 100 万粒をキラキラさせる語彙が揃っているか**である。前の 2 つは通った。3 つ目は**揃っていない**ので、持っているもので組み立てた (下記「踏んだもの」)。

![100 万粒が瞬く 3 秒](https://i.gyazo.com/ed8b36660a65ab205fa35272a5793b4c.webp)

> 撮影範囲: 走っているスケッチの面だけ (`mokume mcp` の観測が書き出した絵で、画面は撮っていない)。1 フレームおきに 90 枚・30fps・3 秒を 720 幅へ縮めたもの。**1 枚では読めないものを 2 つ見てほしい** — 粒がフレームごとに瞬いていること (`.wander` が粒ごとに違う向きへ押す) と、星雲が膨らんでは縮むこと (渦の強さを緩く上下させている)。

## 走らせる

開発は CLI から。

```bash
mokume run .      # 作って走らせる
mokume watch .    # 保存したら作り直して差し替える
mokume mcp .      # 走っているスケッチを外から観測する
```

**窓は設定の半分の大きさで開く。** 面は 3840x2160 なので、窓は 1920x1080 相当から始まる。書き出した絵が 4K であることは観測の `size` が名乗る。

## 触る

| 手 | 起きること |
| --- | --- |
| 動かす | 粒がゆるく指先へ寄る。星雲がそちらへ傾いで歪む |
| 押す | 指先から強く逃げる。押した場所に**青い輪**が出る |
| 離す | 力が消え、渦が押しのけた跡を巻き取っていく |
| ホイール | 視点が寄る・引く (0.75〜1.5 倍に締めてある) |

![押している場所から粒が逃げる](https://i.gyazo.com/bf4a4e26418b6184488f62045cbc6f30.png)

![押した点から粒が逃げ、離すと渦が跡を巻き取る 3.6 秒](https://i.gyazo.com/8f0961687f0619ee36e32cd4720ea5c4.webp)

> 撮影範囲: 走っているスケッチの面だけ (`mokume mcp` の観測が書き出した絵)。**外から `mouseDown` / `mouseUp` を送って撮っている** — 前半が押している間 (面の右上・3400, 400)、後半が離した後。1 フレームおきに 110 枚・30fps。押した点から星雲がえぐれ、離すと渦がその跡を巻き取っていくところを見てほしい。

**触られるまでは何も積まない。** `mouseX` / `mouseY` の初期値は 0 なので、そのまま読むと**面の左上へ引く力が常時かかる**。ポインタが窓の外にあるときも同じ値が返るので、位置そのものからは見分けられない — 出来事が届いたかどうかで見ている。

### 押している間は視点を止める

**画面の位置から空間の点を求める道 (`spacePosition`) は、視点に依存する。** だからマウスを止めていても視点が揺れれば**指先の点は空間を移動し続ける**。粒はその軌跡に沿って押しのけられるので、えぐれた跡が 1 点に定まらず尾を引く。触れている間だけ視点の揺れを止めると、押した点の周りがきれいに空く。

### 印は面の座標へそのまま置く — 2 次元の図形は視点の変換を通らない

**はじめは指先の 3 次元の点を `translate` して円を置いていた。それが間違いだった。**
`circle` のような 2 次元の図形は**視点の変換を通らず、面の座標へそのまま描かれる**ので、
渡した点の x / y がそのまま面の位置として読まれる。画面の中心では両者がほぼ重なるが、
**離れるほどマウスとずれる**。

**面の四隅 (200, 200) … (3640, 1960) へ円を描いて確かめた** — 視点が既定より遠い
(2340 対 1871) のに、円は縮まず四隅のまま出た。立体 (粒の板) は視点の変換に乗るので、
**同じ `translate` の下で立体と 2 次元の図形が別の場所へ行く**ことになる。

逆に、**逆投影そのものは正しかった**。`mouseX` → `spacePosition` → `screenX` の往復は
3000 に対して 2999.998 を返し (面の座標で 0.002 画素)、`screenX` は視点も正しく見ている
(中心から 500 の点が 2319.7 = 500 × 1871 ÷ 2340 の位置へ投影される)。

**だから印は `circle(mouseX, mouseY, …)` と面の座標のまま置く。** 力が効く 3 次元の点が
投影される先は `screenX` / `screenY` で、それはこの面の座標なので、両者は画面の上で揃う。

### 視点をドラッグで回す形は入れていない

**粒の板がビルボードではないので** ([mokume#1043](https://github.com/mokume-metal/mokume/issues/1043))、視点を大きく回すと板が edge-on になって痩せる。自動の揺れを yaw ±0.62 / pitch ±0.45 に抑えているのはそのためで、`orbitControl()` を置くとこの抑えが外れる。

## どの mokume で描いたか

**`Package.resolved` が固定している版がそのまま答えで、コミットしてある。** この作品のコミットを checkout すれば mokume も当時の版に戻るので、別の作品が新しい mokume を要求してピンが動いても、ここの再現は壊れない。

**同じフレーム番号からは同じ絵が出る** (mokume の [ADR-0001](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0001-founding-principles.md) 原則 2)。このスケッチは粒を乱数で撒くが、種を `setup()` で決めてあり、時計はフレーム番号から導かれる。**だから 100 万粒が力で動いても、同じ番号のフレームは同じ絵になる。**

**絵のハッシュは持っていない**ので、版を上げて何かが動いたことに気付くのは窓を開けて目で見たときである。

## 何がどう動いているか

**置いているのは力の足し算だけで、星雲の形はそこから出てくる。**

| | |
| --- | --- |
| `.attract` | 中心へ引く。**距離によらない一定の加速度**である (下記) |
| `.swirl` | 面内で回す。**これだけ緩く上下させている** — 渦が一定だと粒は釣り合いの半径へ落ちて動かなくなる |
| `.drag` | 速さに比例して減速する。**極端に弱くしてある** (0.06) |
| `.wander` | 粒ごと・フレームごとに違う向きへ押す。**瞬きの出どころはここ** |
| `.gravity` | 奥行きへ弱く流す。上下の対称を崩す |
| 指先 (`.attract` / `.repel`) | **触られている間だけ 6 つ目として積む** (1 回に効くのは 8 つまで)。上記「触る」 |

**指先の強さは `強さ ÷ 抵抗` で読む。** 抵抗が 0.06 と極端に弱いので、強さ 320 は 5333 の速さまで加速でき、渦 (55 → 917) の 6 倍になって星雲がほどけた (実測)。寄せるほうは渦より弱く 80、押しのけるほうは中心へ引く力 (約 934) を上回る 450 に取ってある。

釣り合いは 2 つの式で決まる。抵抗と渦が釣り合う速さが `渦 ÷ 抵抗`、その速さで回り続けられる半径が `速さ² ÷ 引く力`。コードの数はここから逆に決めてある。

**時間とともに姿が変わる。** 撒き終わった直後は球、数十秒で中心が抜けて輪になる。50 秒走らせても粒立ちは残ったままで、輪は呼吸を続ける。

### 撒くのは最初だけ

`emit` は CPU が 1 粒ずつ書き、書く直前に GPU の完了を待つ (mokume の `Particles.emit`)。毎フレーム撒くと 100 万粒ぶんの書き込みと待ちがそのまま毎フレームの費用になるので、**最初の 24 フレーム (0.4 秒) で撒き切り、以降は力だけで動かしている**。寿命はそのぶん長く取ってある。

**枠を大きく取ることの代償は無い。** 粒は死んだぶんを GPU が詰めて indirect draw で描く ([mokume#760](https://github.com/mokume-metal/mokume/issues/760)) ので、払うのは生きている粒のぶんだけである。生存数を数える段は容量から決まり 1 段が 256 倍を数えるので、100 万は段 3 つで足りる。

### キラキラは、持っているもので作っている

**mokume の粒に明滅は無い。** 色も大きさも `emit` で渡した値のまま、寿命で変わらない (`Shaders/Computations/Particles.metal` の更新カーネル)。瞬きは 3 つの重ね合わせから出している:

1. **`.wander`** — 押す向きが粒ごと・フレームごとに変わる (`mokume_particleDrift` は番号から作るので、再現性は保たれる)。100 万粒が独立に震える
2. **`.bloom`** — 明るい粒だけを閾値で拾って滲ませる。**淡く大きい霞と、濃く小さい星を 1 回おきに撒いてある**ので、閾値を越えるのは星だけになり、霞の中で星が光る
3. **`blendMode(.add)`** — 重なりが明るくなる。ただし**この粒の濃さでは効きが小さい** (下記)

## 速さ (2026-09-07 の実測)

観測 (`mokume mcp`) が返した数字。Apple M3 Max・40 コア GPU・macOS 26.6.2。

| | |
| --- | --- |
| 粒の数 | **1,000,000** — `makeParticles(count:)` は返り、観測の `particles` も同じ数を差し出す |
| 面 | 3840x2160 (観測の `size` が名乗る) |
| 速さ | **60fps 張り付き** — フレーム時間 平均 16.67ms / 最大 16.76ms。`mokume watch` の debug ビルドでも同じ |
| 占有メモリ | 1400–1485 MB |
| 熱 | `nominal` 〜 `fair` (50 秒・約 2,900 フレーム走らせて変わらず) |
| 警告 | 無し (観測の `warnings` が空) |

**撒く 1 フレームだけが重い。** debug ビルドで撒く山を含めて測ると平均 22.2ms・最大 187.7ms になる。100 万粒を 1 枚に載せると CPU がそこで詰まるので、24 回に分けてある。**撒き終われば debug でも 60fps に張り付く。**

## 踏んだもの

### 1. 粒の混ぜ方が、道具の説明どおりに書くと選べない

`makeParticles(count:)` の説明が出す例は `setup()` で作る形である。

```swift
func setup() {
    dust = try? makeParticles(count: 20000)
}
```

**そう書くと、粒の混ぜ方を選ぶ道が消える。** 粒の板は `createShape` で作られ (`Canvas+Particles.particleQuad()`)、**そのときの混ぜ方を形ごと保持する** — 描くときは `placeFromGPU` が `run.mode` を設定して描くので、後から `draw()` で `blendMode()` を呼んでも粒には効かない。ところが `setup()` は「どのフレームにも属さない」ので、そこで積んだスタイルは警告付きで無視される。

```
mokume: スタイルの積み降ろしはフレームの中でだけできます。初期化のときに積んだスタイルは
どのフレームにも属さないため、無視しました
```

**逃げ道は、粒をフレームの中で作ること。** `draw()` の中で `blendMode(.add)` → `makeParticles` の順に呼ぶと効く。

**効いていることはハッシュで確かめた。** 当時この作品はまだ絵を書き出す口を持っていたので、同じフレームを `.add` と `.blend` で書き出して突き合わせられた (`d0c1f80a…` と `530bea75…` に割れた)。**ただし絵の差は小さい** — 64x36 に落とした平均輝度で 42.81 対 41.26 (3.8%) で、星の粒が既にほぼ不透明なので加算にしても足せるぶんが少ない。**この作品で光っている見た目の主役は `.bloom` のほうである。**

### 2. 粒の初速は、面の中にしか向かない

`emit` の `angle` は面内の角度で、GPU へ渡る粒の速度は `vz = 0` である (`Particles.emit`)。**3 次元へ放射状に撒く指定が無い。**

出る場所は `Emitter.sphere` で 3 次元に散らせるので、この作品では**初期位置を球にし、奥行きの動きは力 (`.wander` の 3 成分と `.gravity` の z) のほうから作っている**。

### 3. 粒の板はビルボードではない

粒は `plane(1, 1)` をワールドの XY 平面に貼った四角である (`particleQuad()`)。置き場所の行列は軸に沿った拡大と平行移動だけなので (`Particles.metal`)、**視点を回すと板が edge-on になって痩せる**。

そのためこの作品は**視点の振れを yaw ±0.62 / pitch ±0.45 ラジアンに抑えてある**。立体感は板の向きではなく、奥行きの遠近と小さな視差から出している。`orbitControl()` を置いて利用者に回させる形は、この理由で採れなかった。

### 4. 引く力が距離によらないので、抵抗があると全粒が同じ半径へ落ちる

`.attract` は中心への向きを正規化してから強さを掛ける (`Particles.metal`) ので、**距離によらない一定の加速度**である。抵抗と組み合わせると、粒は初期の速度のばらつきを失って**釣り合いの半径 1 本へ収束する**。

**実測**: 抵抗 0.45 で回したところ、10 秒 (600 フレーム) で細い輪 1 枚になり、粒立ちが消えて滑らかな帯になった。100 万粒である意味がその時点で無くなる。

逃げ方は 3 つ重ねた: **抵抗を極端に弱くする** (0.45 → 0.06)、**初速の幅を広げて軌道を多様にする** (`speed: 0...500`)、**渦の強さを緩く上下させて釣り合いの半径そのものを動かし続ける**。

これは不具合ではなく、力の仕様からくる帰結である。**ただし「100 万粒を撒いて長く回す」使い方では、避け方を知らないと必ず踏む。**
