# Cast — 1 つの塊が、向きによって別の形の影を落とす

![床に円の影が立っている。塊は左上に浮いていて、影の輪郭だけが朱で引かれている](https://i.gyazo.com/d78d55afe612f5857a288b336c31ee4f.png)

制作トラック ([mokume ADR-0022](https://github.com/mokume-metal/mokume/blob/main/docs/decisions/0022-production-track.md)) の 12 本目。

**形は物の側ではなく、光の側にある。** 置いてある立体は塊が 1 つと床が 1 枚だけで、絵になっているのはそのどちらでもなく**影**である。塊は読めない形をしていて、3 つの決まった角度で止まったときにだけ、床の影が円・三角・四角になる。

11 本目の [Tempo](../Tempo/) は「光を 1 つも置いていない」ことを名乗った作品だった。ここはその裏返しで、**works で影を落とす 1 本目**である。光そのものは Grain・Helmet・Quarry が置いているが、**影の口 (`shadows` / `castShadow` / `receiveShadow` / `shadowRange` / `shadowDetail` / `shadowBias`) と材質の `ambient` は、作品 11 本のどれも通っていなかった**。

![12 秒でひと回りする](https://i.gyazo.com/8c7e7af68b14b47041bce173a70d2087.webp)

> 撮影範囲: 走っているスケッチの面だけ (`mokume mcp` と同じ観測の区画へ要求を置いて書き出した絵で、画面は撮っていない)。**等速** — 6 フレームおきに 120 枚撮り、撮れた間隔は 0.100 秒でそろっていたので、そのまま幅 720・10fps で並べた 12 秒である。四角 → 円 → 三角 → 四角 と渡り、**同じ床の同じ場所で形だけが入れ替わる**。

## 走らせる

```bash
mokume run Cast -c release    # 作って走らせる
mokume watch Cast -c release  # 保存したら作り直して差し替える
mokume mcp Cast               # 走っているスケッチを外から観測する
```

**`-c release` で走らせること。** 走り出してからはどちらも 60fps を保つが、**立ち上げが debug では 17 秒**かかる (release は 0.23 秒)。塊を彫るのも、影の被覆を数えるのも、最初の 1 フレームで 1 度だけ走る CPU の仕事なので、最適化の有無がそのまま出る (下記「速さ」)。

## 触る

| 操作 | 効くもの |
| --- | --- |
| ドラッグ | **塊を回す。** 画面のどこを掴んでも、下の定規と同じ物差しで 0…360° へ写る |
| Space | 止める / 動かす。手で回していたときは、いちばん近い姿勢から譜へ戻す |
| ← → | 2° ずつ回す |
| 1 / 2 / 3 | 揃う角度へ飛ぶ |

**揃う角度は手で探せる。** 影が形になるのは 120° ごとの 3 か所だけで、そこから 10° も外れると読めなくなる。定規の朱い印と、右下の名乗り (○ / △ / □) が、いま揃っているかどうかを示す。

## どの mokume で描いたか

**`Package.resolved` が固定している版がそのまま答えで、コミットしてある。** この作品のコミットを checkout すれば mokume も当時の版に戻るので、別の作品が新しい mokume を要求してピンが動いても、ここの再現は壊れない。Pond・Quarry・Tempo と同じ `v0.7.1` である。

**同じ角度からは同じ絵が出る。** 絵は角度の関数で、スケッチが持つ状態は再生位置と「手で回しているか」だけである。乱数も雑音も使わず、`frameCount` も読まない。時計 (`deltaTime`) を読むのは再生位置を進める 1 箇所だけで、そこから下へは角度しか渡らない。

姿勢 1 (120°・三角) へ飛び、姿勢 2 を挟んでからもう一度姿勢 1 へ戻して、観測が書き出した 1920 × 1080 の PNG を突き合わせた (2026-09-12・release):

| --- | --- |
| 1 度目の 120° | `a1d547be…` |
| 240° を挟んで戻した 120° | `a1d547be…` |

**1 バイトも違わない。**

## 何がどう動いているか

### 影は「高さに比例した平行移動」でしかない

向きを持つ光の下では、点の影は次の式で決まる。仰角 φ・方位 e の光で、高さ `Y` の点 `(X, Z)` が床へ落ちる先は

```text
影 = (X, Z) + κ·Y·e        κ = cot φ
```

**κ·Y の項は、塊をどれだけ回しても変わらない** — 回すのは縦軸まわりなので高さが動かないからである。だから 3 つの姿勢の影は「同じ 1 つのずれを受けた、向きだけ違う 3 枚」になる。

ここから、この作品が**斜めの光でしか成り立たない**ことが出る。光を真上から差すと `κ = 0` になってずれが消え、**3 つの影は完全に同じ絵になる** — 円と三角と四角を作り分けることが原理的にできなくなる。ずれの総量 `T = κ·h` (`h` は塊の高さ) が、3 つを作り分けられる余地そのものである。

### 彫り出しは「3 つとも内側」だけを残す

塊は距離の関数で決まる。

```text
f(p) = max_j  d_j( σ_j(p) )          j = 0, 1, 2
塊 = { p : f(p) ≤ 0 }
```

`d_j` は姿勢 `j` で狙う図形の符号付きの距離、`σ_j` は姿勢 `j` で回してから床へ落とす写像である。「3 つとも内側」という条件を、そのまま「3 つの距離のうちいちばん大きいもの」として書いただけである。

**はみ出しはここから構造上ゼロになる。** 塊の点はすべて `f ≤ 0` を満たし、それは「3 つの姿勢のどれで落としても狙いの内側」という意味なので、**影が狙いの外へ出ることは定義から起きない**。起こるのは欠けだけである。

### 欠けは三角形の角から出る

3 つの狙いは**面積をそろえてある**。そろえないと、いちばん小さい図形が他の 2 つを削り落として全体の被覆を下げる。等面積にすると寸法はこうなる:

| 図形 | 寸法 | 外接半径 | 内接半径 |
| --- | --- | --- | --- |
| 円 | `r` | `1.00 r` | `1.00 r` |
| 正三角形 | 一辺 `2.694 r` | `1.555 r` | `0.778 r` |
| 正方形 | 一辺 `1.772 r` | `1.253 r` | `0.886 r` |

**三角形の角は円より 1.55 倍遠い。** 円の影に収まる点しか残せないので、三角形の 3 つの角がいちばん埋まりにくい。実測 (立ち上げに 1 度数える・`Cover`) がそれをそのまま出している:

| 姿勢 | 狙い | 埋めた割合 | はみ出し |
| --- | --- | --- | --- |
| 0° | 円 | **96.89%** | 0 |
| 120° | 三角 | **91.95%** | 0 |
| 240° | 四角 | **93.86%** | 0 |

はみ出しは床へ敷いた格子 (256 × 256・1 画素 2.6 単位) で数えていて、**縁の 1 画素ぶんは量子化の誤差として見逃している**。上の「構造上ゼロ」が保証しているのは式のほうで、この数は**式のとおりに書けているかの検算**である (0 でなければ写像か距離が間違っている)。

![240° で四角の影が立つ](https://i.gyazo.com/5b52eff5a8dbeb2c79d460f17faff081.png)

> 撮影範囲: 観測が書き出した絵 (姿勢 1 と 2)。朱の輪郭が狙いで、影との差がそのまま上の表の「欠け」である。**三角形の角**と**四角形の角**が少し丸いのが見える。

**向きは掃いて決めた。** 三角形と正方形の向きを 10° 刻みで動かし、`T` も 1.4 / 1.8 / 2.2 の 3 通りで回して、3 つの狙いの最小被覆がいちばん高くなる組を選んだ (使い捨ての探索を別に書いた・作品には測る口を持たせない)。**どこを選んでも 89–92% の帯に収まり**、いちばん良い組でも 92.35% だったので、**調整の出来不出来には賭けていない**。

### 面は箱を積まずに切り出す

塊は 370 万個の節に並べた `f` から、**符号が変わる辺を見つけて面を張って**いる (surface nets)。セルの箱をそのまま積む Quarry のやり方だと、塊の階段がそのまま影の階段になり、**影が主題の作品では狙いの図形の輪郭が段々になって出てしまう**。

法線は `f` の傾き (中心差分) から取る。**面ごとではなく節ごとに向きが決まる**ので、光の当たり方が連続に変わり、細かい面がモアレにならない。

焼いた形は **72,028 枚の三角形 (216,084 頂点)** で、毎フレームの描画回数は **1** である。

### 光は 1 本しか置かない

mokume で影を落とすのは**向きを持つ光 (`directionalLight`) の 1 本目だけ**である。点光源もスポットも、置けば明るくはなるが影は落とさない。この作品は影が主題なので、2 本目を足すと影を落とさない光が絵を持ち上げて、影の濃さだけが薄くなる。

**影の濃さを決めているのは底上げの光 (`ambientLight`) と、床がそれをどれだけ返すか (`ambient`) である。** 影が薄くするのは向きを持つ光のぶんだけなので、底上げのぶんがそのまま影の明るさになる。床の `ambient` を 158 から 104 へ下げると、影が墨に寄って図として読めるようになった。

### 影の焼き付けはフレームの終わりに 1 度走る

焼き付けは「光から見た平行投影」で、中心は**いまのカメラの注視点**、一辺は `shadowRange` である。切り取った外は「遮られていない」として返るので、**足りないと影が切れる**。塊と床の狙いが両方入る最小の箱を寸法から計算して渡してある (2552 単位)。

**既定 (面の対角・2203 単位) でも、この場面では切れなかった。** 差が 1.16 倍しかないので見た目には出ない。わざと 420 単位まで絞ると、三角の影が中央の小さな切れ端だけになり、**足りないとどう壊れるか**が見える (絵が暗くなるのではなく、影が四角く削げる)。明示しているのは、寸法を変えたときにこの偶然が続く保証が無いからである。

**手元の表示のために `noLights()` を呼んでそのまま終えると、そのフレームの影が丸ごと消える。** 焼き付けはフレームの終わりに 1 度だけ走り、**そのときの光**を読むためで、mokume の参照スケッチや Quarry の手元表示はこの形を取っている。ここでは光を消さずに手元の表示を描いている (実測した・下記「踏んだもの」)。

### 止まっている時間が拍を作る

12 秒でひと回り。4 秒ずつの 3 区間で、それぞれ **2.4 秒止まって 1.6 秒で 120° 回る**。3 回で 360°、つまりひと回りして同じ姿勢へ戻る。

**止まらずに回し続けると、影が形になる瞬間が通り過ぎてしまう。** 何を見ればよいのかが分からなくなるので、止まる時間のほうが長くしてある。

床の朱い輪郭は**揃ったときにだけ濃くなる**。出しっぱなしにすると、影ではなく輪郭のほうを見てしまう。濃さは時刻ではなく**角度**から出しているので、手で回しても譜で回しても同じ角度なら同じ濃さになる。

![円から三角へ渡る 1 回の送り](https://i.gyazo.com/9b37b558412a379c15d002b74d634ad7.webp)

> 撮影範囲: 観測が書き出した絵。**等速** — 2 フレームおきに撮った 56 枚を幅 720・30fps で並べた 1.9 秒で、円から三角へ渡る 1 回の送りである。`expoInOut` で 1.6 秒かけて 120° 回り、**着く直前で急に遅くなる**ので、形になる瞬間が伸びて見える。

## 速さ (2026-09-12 の実測)

Apple M3 Max / macOS 26 / mokume `v0.7.1` / 1920 × 1080。

| | release | debug |
| --- | --- | --- |
| 彫り (370 万節へ `f` を並べる) | 14.8 ms | 3,993 ms |
| 焼き (面を切り出して 1 つの形へ) | 104.1 ms | 5,327 ms |
| 数え (3 つの姿勢の被覆) | 108.8 ms | 7,745 ms |
| **立ち上げ合計** | **0.23 秒** | **17.1 秒** |
| 走り出してからの fps | 60.0 | 60.0 |

**70 倍の差が出るのは、立ち上げの仕事が全部 CPU にあるからである。** 走り出してからは GPU の仕事しか残らないので、debug でも 60fps を保つ (1 フレームの最大 16.7–18.3 ms)。記憶は 580–630 MB。

塊の描画回数は毎フレーム **1**。三角形 72,028 枚・頂点 216,084 で、影の焼き付けは塊が回るたびに走り直す。

## 直したこと

### 画面が真っ黒になった

`ambientLight(0.52, 0.52, 0.53)` と書いた。**光の強さは塗りと同じ 0…255 の尺度**なので、0.52 は「255 分の 0.52」になり、光を置いていないのと同じになる。絵は出るので (真っ黒な床と真っ黒な塊が出る) 気付くまでに時間がかかった。`LinearRGBA` を渡す口 (`.linear(red:green:blue:)`) は 0…1 なので、**同じ名前の関数で尺度が 2 つある**ことになる。

### 塊が自分の影で汚れた

塊の表面に細かい縞が出ていた。光と平行に近い面で、焼いた 1 画素の中の奥行きの差が影として出るアクネである。塊は凸なので自分に落ちる影は無く、`receiveShadow(false)` で受け取りを切ると消えた — 絵は何も失わない。

### 塊が階段でモアレになった

最初はセルの箱をそのまま積んでいた (Quarry と同じやり方)。1 辺 5 単位の面が画面では 1 画素を割るので、**面の向きで決めた明るさが干渉して砂嵐のように見えた**。面を距離の 0 面から切り出す形に変え、法線を `f` の傾きから取るようにして消えた。**影の輪郭が段々にならなくなったのも同じ変更の効き目**である。

### 塊が自分の影に重なって、形が読めなかった

塊の下端を床から 150 単位に浮かべていたので、画面の上で塊と影が重なった。影の中心は `κ·(中心の高さ)` だけ横へずれるので、**高く浮かべるほど離れる**。520 単位へ上げた。彫り出しは中心からの高さしか見ないので、ここを動かしても塊の形は変わらない。

### 床が寝すぎて、円も四角も同じに見えた

見下ろす角度を 45° にしていた。床の円は見下ろす角度 θ の楕円 (短軸 / 長軸 = sin θ) になるので、45° では 0.71 — 円と四角の見分けが「潰れ方の違い」になってしまう。**67° へ起こすと 0.92 になり、円が円に見える**。真上から見れば歪みは消えるが、そのときは塊が板にしか見えない。

### debug の立ち上げが 46 秒かかった

被覆を数えるのに、光の線を 200 段に刻んで距離を引いていた。**線に沿った `f` は下に凸**なので (凸な柱 3 本と板の共通部分である)、刻んで舐めずに挟み撃ちにできる。面を切り出す側も、セルごとに 8 個の配列を確保していたのと、同じ頂点の傾きを面ごとに引き直していたのをやめた。46 秒 → 17 秒。

## 踏んだもの

1. **フレームの終わりに `noLights()` を呼ぶと、そのフレームの影が黙って消える。** 焼き付けがフレームの終わりに 1 度だけ走り、そのときの光を読むためである。手元の表示を「既定のカメラ + `noLights()`」で描く形は mokume の参照スケッチにも Quarry にもあるので、**影を使う作品と手元の表示を同時に持つと必ず踏む**。mokume へ戻した ([#1151](https://github.com/mokume-metal/mokume/issues/1151))
2. **光の強さの尺度が 2 つある。** `directionalLight(0.7, 0.7, 0.7, …)` は「255 分の 0.7」で、`.linear(red: 0.7, …)` は 70%。塗りと揃えた設計として筋は通っているが、**間違えたときに出るのが真っ黒な絵**なので気付きにくい。mokume へ戻した ([#1152](https://github.com/mokume-metal/mokume/issues/1152))
3. **`shadowRange` の既定 (面の対角) は、この場面ではたまたま足りていた。** 2203 と 2552 の差なので切れ方が見えなかった。420 まで絞って初めて「影が切れる」ことを確かめられた
4. **観測の区画は走っているスケッチの数だけ取り合う。** debug の計測のために 2 つ目を走らせたまま `observe` を呼び、**古いほうの絵と数字を読んでいた**。報告に `stamp` が載るので、作り直した版と突き合わせれば気付ける

**踏まなかったもの**: `plane` は `rotateX(π/2)` で寝かせればそのまま影を受けた。`createShape` に 21 万頂点を渡しても描画回数は 1 で、毎フレーム置き直しても 60fps を割らなかった。`shadowDetail(4096)` は素直に効いた。
